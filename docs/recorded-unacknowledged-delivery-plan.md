# Recorded messaging performance plan

**Status: runtime replacement design, with private experiments implemented separately.** Step 4.28 implements the [comparison benchmark](nanomsg-comparison.md). Step **4.29**, framework **0.4.31**, adds [focused stall diagnostics and the current-log SPSC experiment](https://github.com/smangano/angaria/blob/aade0f6a0da98f2439cacd44396b67efe1f31e75/docs/stall-study.md). Public runtime admission and later stages remain planned. This document itself changes no runtime guarantee.

Step 1's [independent messaging protocol design](independent-messaging-protocol.md) makes the ownership and commit choices concrete. Before 1.0, backward compatibility is not required: replace the superseded runtime and recreate Sessions after incompatible format changes. Do not maintain parallel runtime engines, old-format attachment, migration converters or compatibility adapters. Version checks still reject unsupported storage before access. Preserve the useful message, replay and processing guarantees explicitly; dropping binary/API compatibility is not permission to silently drop those guarantees.

The performance direction is to remove Session-wide coordination from established messaging while retaining mandatory recording and optional application acknowledgments. The first target is local interprocess communication through fixed one-to-one connections. Explicit fan-out and Source Queue Set fan-in extend that path in milestones 6 and 5 respectively. A fan-out publication goes to every accepted destination; it does not choose one worker from a pool.

## Architectural target

After Tasks are registered and Queues/Queue Sets are established, two independent connections must be able to send and receive without acquiring a common Session lock or modifying common Session transaction state. This applies to recorded/unacknowledged delivery and to acknowledged delivery on the new protocol. Publication-ID issuance, normal empty receives, acknowledgment, release and ordinary outcome lookup must not reintroduce that coordination through another API call.

Independent connections have disjoint producer-stream and consumer/Source ownership. Connections that deliberately share a producer stream, Source or fan-out acceptance group may coordinate scheduling/backpressure within that scope; this does not justify Session-wide serialization of unrelated owners.

The Session establishes identity, capacity reservations, ownership, immutable schemas and topology. Administrative changes may coordinate setup or affected endpoints; an unrelated established connection must continue communicating while the administrative gate is held. Existing Session metadata can remain available as immutable cached context. Normal messaging must not reuse the Session's operation journal, allocation tail, operation generation or append-manifest chain, including through a replacement global sequencer.

| State | Intended ownership and coordination |
| --- | --- |
| Registry definitions, configuration and topology changes | Session administration; checked endpoint snapshots plus an explicit affected-endpoint transition protocol. |
| Publication identity, append space and acceptance commit | Producer-owned log stream, including its incarnation and restart rules. Prefer producer-owned reserved regions or segments so a payload can be shared across destinations. The first design step fixes physical placement and references. |
| Ring publication and credit | One producer and one consumer per connection, using qualified native atomics and endpoint-local generations. |
| Source selection, borrow and consumer progress | The owning consumer/Source and its input connections. |
| Acknowledgment, release and redelivery evidence | Connection/Source-scoped progress and recovery records; no Session journal transaction. |
| Retained-log budget | Reserve bounded producer quotas/segments during setup or an explicit growth operation; do not update a shared Session byte counter on every message. |

Removing the gate requires a new commit/recovery protocol, not merely finer locks around the existing journal. A global atomic tail or counter would still introduce shared per-message coordination and would not resolve abandoned reservations or crash recovery. The implementation steps below are proposed for review before development begins; this document enables no new runtime behavior.

The protocol review must bound aggregate physical log reservation, separately reserved acknowledgment/recovery storage, and per-process mapping count and address-space use. Reuse producer mappings across its connections where appropriate. The first bounded profile must not depend on per-message file growth or mapping creation; any later segment transition needs explicit budget, mapping and peer-discovery rules rather than an implicit fallback to Session allocation.

## Existing behavior and proposed boundary

The [current transport contract](native-transport.md) implements direct Queue send, retained outcome lookup, and one-Active-Queue Source receive with acknowledgment, release and configured loss. Multiple-Queue Source selection, Publishing Queue Set delivery and notification waiting remain later roadmap work. Public declarations are not evidence that these paths are implemented.

Current operations use the [Session mutation gate and journal](concurrency.md). A runtime access recovers and validates committed history; publication ID issuance is a separate FixedState transaction. Send appends immutable Publication data, destination receipts and a manifest, then applies recorded state updates. Receive establishes an issued receipt and pin; acknowledgment records terminal progress. Existing `release()` returns a delivery to Pending for redelivery. It is not an unacknowledged consume operation.

The proposed profile retains the concepts of producer ownership, Publishing Queue Set destinations and Source Queue Set inputs. It needs a separate protocol and delivery contract. It must not silently change acknowledged delivery, reinterpret `DeliveryPolicy::AllowLoss`, or expose current mutable ring structures without their required gate. Allowed loss still records delivery progress in the existing protocol.

## Required contract

| Dimension | Proposed requirement |
| --- | --- |
| Acceptance | Every accepted message is committed to its replay log before it becomes visible to any consumer or send reports acceptance. |
| Replay evidence | The committed record identifies the producer and incarnation, sequence, exact schema/header/payload, destination snapshot and per-destination acceptance outcome. |
| Fan-out | `AllDestinations` is the default. An explicitly selected `Partial` policy records exactly which destinations accepted and which did not. |
| Destination availability | Freeze whether an offline destination is eligible for acceptance and how connection liveness is established. Available ring credit alone does not establish a live consumer. |
| Application progress | Recorded/unacknowledged delivery requires no application acknowledgment or per-message processing receipt. Optional acknowledged delivery retains explicit acknowledgment/release, replacement redelivery and independently recorded destination progress. Acceptance and successful application processing remain separate boundaries. |
| Ordering | Preserve producer publication order and each Queue's accepted-message order. The new protocol proposes no mandatory Session-wide commit order across independent producers; stronger replay ordering requires a separately specified optional trace. This explicitly revises the earlier plan, as detailed below. |
| Failure scope | Process termination on a running system with coherent local mappings, as in the current native contract. No power-loss durability, synchronous disk-flush or network-filesystem guarantee is implied. |
| Retention | Keep all accepted records for the retained Session/log lifetime. Exhausting the configured bound returns `LogFull`; consumer progress alone cannot authorize deletion. |

An interrupted call may have committed without returning its result. It must not turn a committed acceptance into a known rejection. Retain an explicit caller-visible publication identity for uncertain-result lookup and deduplication. Step 1 chooses owner-local ID issuance within a persisted claim incarnation, avoiding a separate Session transaction; acceptance remains the producer log commit. Public signatures may evolve before 1.0.

Preserve the common `MessageHeader`, `MessageView` and owning `Message` model. An owning copy must preserve the exact logical header, payload bytes and decoding dependencies beyond the endpoint/borrow lifetime. A mode-specific receive handle carries no application-acknowledgment obligation; any storage or mapping lease it owns is a separate resource contract. Do not reuse `DeliveryToken` in a way that implies the existing acknowledgment obligation or silently changes existing `Delivery` behavior.

## Log authority and connection rings

A proposed connection has one producer and one consumer, with a bounded single-producer/single-consumer (SPSC) ring. Concurrent application threads must not share an endpoint in a way that violates that ownership. Mapping setup and native atomic bindings occur when the connection opens, rather than for every message. The protocol must qualify alignment, release/acquire ordering and supported ABI profiles; it cannot assume ordinary mapped-byte accesses are atomic. A producer owns its append/commit state independently of unrelated producers and consumers. Reserving physical capacity must remain distinct from establishing which logical bytes have committed; simply extending an existing-format file is not a compatible implementation of that distinction.

The payload is written once into immutable logged storage. Ring entries carry checked references to committed payloads, with connection identity, sequence and generation sufficient to reject stale or wrong-log references. Each consumer borrows the same immutable payload through its own mapping lease. Copying a reference into several connection rings avoids a payload copy per destination without requiring each consumer to own or free the payload. Reusable payload storage would require a separate reclamation protocol.

The publication identity is issued locally before send so the caller can retain it; Queue sequences are assigned within acceptance preparation. The complete allocation and destination outcome must be established before commit. The normal sequence is:

1. Validate producer/connection ownership, message bounds, payload rules, destination membership and result capacity using checked connection metadata.
2. Check log space and all required connection credits before accepting. Finish any operation that can produce a known rejection before changing published heads.
3. Write the complete immutable record, including destination outcomes and the sequence/order metadata, into reserved log space.
4. Publish the log commit with the required native ordering. This is the acceptance authority.
5. Expose references in the accepted destinations' rings and return the recorded outcome.

Record materialization or a ready-looking ring slot is not sufficient evidence of acceptance. Consumers must rely on the committed record and their recorded destination membership. Interrupted append recovery must distinguish committed records from incomplete reservations before exposing or replaying either.

## Fan-out, capacity and crashes

For fixed connections with one producer owning all outbound rings, an `AllDestinations` capacity check can establish that every destination has credit before the append. Consumers only return credit, and another producer cannot consume it. Under those assumptions, a normal `WouldBlock` result can leave every destination unchanged. Concurrent sends, connection replacement or another writer would invalidate that reasoning and require additional coordination.

This profile proposes flow-controlled rings: do not overwrite an unread entry, and never reclaim logged payload bytes while they are borrowed. That differs from the existing ring cache, whose overwritten entries can be recovered through retained history. A slow or disconnected destination can therefore block the default fan-out path even when other destinations are ready. A bounded wait must retain its deadline across retries; zero-time admission can return `WouldBlock`. Log exhaustion remains a distinct `LogFull` condition.

`Partial` must be explicit. Determine the eligible subset and record each destination's outcome in the committed publication. A destination excluded from that acceptance must not later appear to have accepted it. If every destination rejects, create no accepted publication/log record, preserving the existing zero-acceptance boundary. Recovery can still settle an earlier uncertain operation; this rule does not change uncertain-outcome handling. Retry rules, if offered, need their own recorded identity and outcome contract; they cannot be inferred from a volatile ring state.

Offline-destination admission is a separate policy decision. The existing acknowledged profile can accept while its consumer is offline. A new profile could retain that behavior or require an available connection, but it must define availability, disconnect detection and the resulting timeout/rejection behavior before implementation. A free ring entry is storage capacity, not proof that a peer can receive. The benchmark must report these policies explicitly rather than treating credit availability as equivalent to a socket having an available downstream connection.

Publishing multiple ring heads is not one atomic operation. If the producer dies after log commit, some consumers may already have observed references while others have not. The committed destination list can establish all-destination acceptance, but it does not ensure that all live notifications completed. Strict crash-atomic acceptance depends on that shared log commit predicate, not on the collection of head stores. A postcommit ring-publication delay or failure leaves accepted data not yet exposed; it cannot become a known rejection or `WouldBlock` result.

Also qualify a producer that remains live but is paused after commit and before ring publication. Consumers must be able to discover their newly committed records without taking over that producer's ownership or rescanning the retained prefix. The protocol review fixes the committed-range catch-up and late-descriptor rules, including pause/resume behavior; proving recovery after process death alone is insufficient.

Before a runtime profile is admitted, select and qualify its restart policy. Rebuilding/catching up connection rings from committed records can restore discoverability, but volatile consumer cursors cannot prove which messages an application already processed. Replay can consequently duplicate delivery. Starting at the live tail instead is a different policy that may skip accepted messages in live delivery, even though they remain available for explicit replay. Neither choice may be presented as acknowledged or exactly-once processing.

## Source fan-in and local ownership

A Source selects among its configured incoming connections; a Publishing Queue Set sends to its configured outbound destinations. These are separate operations. Strict priority, fair selection and waiting policy need defined behavior and qualification rather than being borrowed from declarations of future native functionality. Preserve each input's order; a merge of several inputs does not automatically reproduce commit order.

Receiving a borrowed view can consume its ring entry while a **local borrow lease** keeps the payload mapping usable. Returning ring credit or ending this lease is resource management, not application acknowledgment. The API must define whether a view ends on the next receive invocation, explicit loan release, Source close or connection teardown, including a receive that times out. An owning copy is required when application work outlives that boundary. Copying a span does not extend the lease.

The immutable log remains the storage authority after connection credit returns. Log retirement or deletion must respect outstanding mapping leases, not merely ring cursors. A process-local mapping lease does not protect another process: cross-process reclamation would require a qualified shared lease, epoch or equivalent protocol. For the first profile, retain the append-only log and fail with `LogFull` at its bound. Replay retention includes the exact decoding definitions and destination metadata, not payload bytes alone. Future rotation or archival must preserve that history and define recovery and retention ownership before reclamation is allowed.

## Commit order and optional delivery trace

The current shared append/journal authority provides an order across producer operations, and step 4.29 preserves it in the current-log experiment. The earlier plan required that order in the eventual profile too. The revised architecture drops that requirement for the new protocol: preserve order within each producer stream and Queue, and retain exact message identities, destination outcomes and decoding context. Independent producer streams have no asserted total commit order. This is a documented breaking format/contract change; recreate development Sessions rather than interpreting old logs under the new rules.

Timestamps alone cannot reconstruct the actual order of concurrent commits or consumer selection. Inspection/export may provide a documented deterministic merge for convenience, but must not present it as the recorded execution order. If an application requests a stronger cross-stream order, an optional trace or other explicitly coordinated profile must define the events, ordering authority and failure behavior and expose its costs separately. A counter reserved before commit is not commit order under crashes.

The required log supports replay of accepted messages and their recorded destination outcomes. It does not, by itself, reproduce which Source input won a race, the order consumers processed messages, clock observations or external effects. An optional delivery trace could record selection/dequeue events when that stronger replay task is needed. Trace collection has separate allocation, ordering, retention and throughput costs. It must not be enabled silently in an ordinary messaging comparison, and message logging must remain mandatory when the optional trace is disabled.

## Optional acknowledgments on the same architecture

Both delivery modes use the same retained immutable messages and producer-owned acceptance authority. An acknowledgment certifies the application's explicit progress according to the selected delivery contract; it does not establish initial message acceptance or introduce synchronous disk flushing. Recorded/unacknowledged delivery does not create unused legacy Pending receipts as the current experiment does.

The acknowledged path needs recoverable, separately owned issuance, pin, release and terminal-progress state. The design must assign each mutable word an owner, define how the peer observes it, and qualify interrupted multiword updates without borrowing the Session journal. Preserve existing public token/incarnation checks, independent destination acknowledgments, release/redelivery behavior and borrowed-message lifetimes. A duplicate or stale acknowledgment must not terminate a different delivery. Bounded reserved progress storage must allow acknowledgment and replacement recovery when the append log is full.

Use the [public receive](native-receive.md) and [native progress](native-progress.md) contracts as the behavior matrix: repeated receive while pinned, explicit close and claim cleanup, unchanged-state failures preserving a borrow, uncertain-result invalidation, dequeue/acknowledgment timestamps and presence, parent/incarnation checks, and counter exhaustion. Step 1 reserves consumer-owned receipt rows to preserve per-message latest progress, rather than requiring an optional execution trace for ordinary receipt inspection. Configured allowed loss is explicitly deferred in the first replacement protocol and returns `UnsupportedPolicy` until separately qualified; it is not silently mapped to another policy.

Keep acceptance synchronous with the producer's log commit. Choosing unacknowledged delivery removes the application-processing acknowledgment obligation; it does not move recording to an optional background best-effort operation. Acknowledgment remains the default processing mode; no requirement to preserve old APIs or Session files adds a second runtime engine.

## Validation and pre-1.0 replacement

The steady-state target is work independent of retained message-history length: no full-prefix scan, full topology reconstruction or Session-level receive-progress transaction for each message. Validate retained state during attachment/recovery, then retain checked schema, topology, mapping and ownership metadata for the endpoint lifetime. Define how configuration revisions, changed claims and connection generations invalidate those handles without a common Session check on each message. Cache use must not permit a replaced or ended owner to continue publishing. Recovery work may scan the affected stream, but another established connection must not acquire that stream's recovery lock or await its owner.

This is not a claim of constant work for arbitrary messages or topologies. Payload copying/validation depends on payload size and schema; fan-out depends on destination count; Source polling depends on its inputs. Continue checking current message bounds, committed references and slot generations. Removing repeated history validation must not remove necessary admission checks or use unchecked pointers from shared storage.

The new protocol requires explicit mapped-layout and synchronization admission for both delivery modes. The design proposes native format 3.0 and a new synchronization revision; exact codecs follow in step 2. Reject unsupported versions before writes or recovery. Replace the old engine at public admission, remove its obsolete runtime branches/tests, and require recreation of development Sessions. There is no old-format reader, dual-engine switch, in-place upgrade or data-migration workstream. Historical benchmark baselines remain reproducible from pinned commits. Update the public API, current format documentation, inspector/export support and primer examples together when implementation actually introduces public behavior.

## Acceptance evidence

- For both delivery modes, established send/ID issuance, receive/empty receive, acknowledgment/release where applicable, and normal outcome lookup acquire no Session mutation gate and write no common Session journal, allocation tail, manifest chain, generation or global commit counter. A held administrative gate does not stop these operations.
- No retained-history traversal or full topology rebuild occurs per ordinary message. Payload/schema work can scale with the current message and fan-out/selection work with configured destinations/inputs. Explicit replay and affected-stream recovery are separately measured scans.
- Every accepted message remains replayable with its original logical header, bytes, decoding definitions, producer/Queue order and exact accepted destinations, including death after commit but before ring exposure. Known rejection cannot leave a new accepted message; uncertain results remain distinguishable.
- Separate tests qualify application acknowledgment, ring credit, mapping lifetime and log retention. Optional acknowledgments never become required to keep recording enabled, and returning credit never implies processing success.
- Independent-process tests cover stopped owners, stale handles, slow/full/offline peers, bounded log exhaustion and recovery while unrelated established connections continue. Independence does not promise immunity from ordinary host scheduling, storage pressure or shared hardware limits.
- Lead performance reports with verified end-to-end latency and completed-publication throughput for both modes, using matched payloads, offered load, topology and wait policy. Keep warm steady streams separate from short bursts, startup/wakeup delay and instrumented attribution. Retain attempts and failures, adequate samples for any reported tails, CPU/native-call/page-fault evidence and plots against the appropriate baseline. Hardware cache-contention analysis is explanatory evidence when the host supports it, not a substitute for latency/throughput.
- Each implementation PR includes its scope-appropriate focused performance unit test or full matched nanomsg benchmark and the actual result. Reuse meaningful existing checks where suitable; do not add tests that merely mirror implementation. Keep noisy hosted wall-time comparisons as reported measurements rather than unqualified hard CI thresholds, and use deterministic work/allocation/scan checks where those reliably express the intended local cost.

Benchmark reporting must lead with end-to-end latency and completed-message throughput, include tails and CPU cost, and retain setup, payload size, fan-out degree, topology, wait policy and offered-load details. Include saturation, slow-reader and bounded-log behavior. Allocation/profile counts can explain a result but cannot substitute for latency/throughput evidence. The [current performance methodology](native-performance.md) remains the baseline for provenance and workload limits; a future comparison must not label semantically different paths as a like-for-like transport speedup.
