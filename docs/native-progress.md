# Reserved delivery progress and claim cleanup

> Historical implementation note: this page describes the superseded runtime or its original qualification. Current format 3.0 and public messaging are documented in [public runtime admission](public-runtime-admission.md) and [the current format](mapped-format.md). Historical source and measurements remain pinned to their recorded revisions.

Milestone 4, step 4.5, framework **0.4.6**, implements private progress operations for the core format **2.2/`0x7`** profile. They build on [history validation](native-validation.md) and [committed payload mapping](native-storage.md#committed-payload-storage-and-append-planning). Step 4.6 enables [public direct send and status](direct-publication.md), core Session creation, and the fourteenth [primer lesson](primer.md#14-send-directly-and-look-up-acceptance). Step 4.7 exposes [public receive, acknowledgment/release, and Source close](native-receive.md) with bound payload views and the fifteenth primer lesson. Step 4.8 adds reserved allowed-loss progress under **2.2/`0xf`** and the sixteenth primer lesson.

**Reserved progress** means updating the mutable receipt and fixed runtime rows that already exist, without appending another record. These operations use the journal's FixedState command area. Acknowledgment can complete when the publication log is full; it does not reclaim history or make append space reusable. This is a log-byte-budget guarantee: local heap allocations, mappings, file operations, and retained-history validation can still occur and fail. It is not an allocation-free or constant-time API guarantee.

Step **4.35**, framework **0.4.37**, separately implements [private producer-owned acknowledged delivery](recorded-acknowledged-progress.md) without this Session journal. That replacement remains private until public admission; the format-2 public operations below retain their existing behavior.

## Private receipt operations

The [progress primitives](https://github.com/smangano/angaria/blob/b4ec8ae/src/delivery_progress.h) take a recovered, gate-bound `RuntimeAccess` and a captured claim or delivery token. The [public Source endpoints](native-receive.md) first authenticate their native Task owner. Generic primitives check the core capability, Session identity, current attached Task incarnation, Thread parent context, complete topology/history, and Source ownership under the guard. Step 4.18 adds a trusted [receive issuance overload](performance-receive-validation.md) that reuses the complete topology/history validation already performed during selection under the same unchanged RuntimeAccess. It retains live ownership/claim/parent and Source/Queue/receipt checks. Models cannot cross an access or mutation boundary; generic issuance and cleanup retain fresh validation. Step 4.19 [resolves fresh issuance directly from the Queue's oldest-pending link](performance-delivery-lookup.md). It checks the exact committed direct Publication, Queue/sequence/link and fresh receipt; full history validation remains. Acknowledgment still searches history for its successor link.

| Operation | Effect |
| --- | --- |
| Issue | Select the chosen Queue's oldest nonterminal Pending receipt, assign a new Source issuance, and install matching Issued receipt and Source pin. Retained history supplies a delivery even when its ring entry has been overwritten. |
| Repeat issue with an existing pin | Return that exact token, message reference, and dequeue time unchanged, before considering fresh Queue selection or exhausted counters. |
| Acknowledge | Require the exact current token, mark its receipt Acknowledged with explicit timestamp presence, advance the contiguous Queue watermark/oldest-pending link, record the last acknowledgment time, and clear the Source pin. |
| Release | Require the exact current token, restore Pending, preserve its historical consumer/issuance/dequeue fields, and clear the Source pin. Queue acknowledgment progress stays unchanged. |
| Release Source | Release its current issuance for the exact current claim, or succeed without mutation if it is idle. Preserve its issuance counter and consumer context. This is the reserved cleanup foundation used by step 4.7 public close and deferred-cleanup ownership. |

A delivery token includes Session, consumer Task/incarnation, Source, Queue, Queue sequence, and issuance. A stale token cannot acknowledge a redelivery. Closing/reopening within a claim preserves its Source counter. A new claim starts a new issuance context on its first fresh issue, while retained receipts keep the older context. Counters reject exhaustion rather than wrapping. Epoch-zero and negative UTC times are valid because presence flags, rather than timestamp values or wall-clock ordering, describe the recorded events.

Ordinary progress uses absolute WriteRange commands. Issue needs 152 encoded bytes, acknowledgment 184, and release 88, all within the 1,792-byte inline limit. The full command stream and every target are validated before mutation; recovery reinstalls absolute values after any partial word application. No progress operation spills into the append arena. A successful private operation updates its gate-bound generation so a caller can issue and then settle that issuance under the same guard. An unresolved interrupted result requires recovery before further progress.

## Publication-aware ReleaseClaim

The compact [ReleaseClaim](concurrency.md#redo-commands-and-append-manifests) frame remains 32 encoded bytes: a command header plus the ending incarnation and release time. The admitted core capability selects its publication-aware execution; legacy Sessions retain their Task-only zero-progress checks. With the separate allowed-loss capability, cleanup recognizes and preserves Lost receipts. ResetBudgets and Retry execution remain unsupported.

Cleanup finds receipts using their retained consumer identity and finds Source ownership through committed immutable definitions. It restores matching Issued receipts to Pending before clearing Source slots, preserving historical receipt fields and Source counter/context. Already Pending and terminal receipts need no state change. It also marks the ending Task detached. Releasing a Process claim includes Thread claims tagged with that captured parent incarnation; a different parent incarnation is outside that cleanup.

Replay never depends on a Source pointer that an earlier pass may have cleared. It also recognizes the immediate successor Task incarnation while finishing a replacement's absolute attachment writes. Complete intent validation rejects writes that could erase the definitions or old identities used for discovery. Publication metadata is scanned without copying payloads; generated live-state writes are bounded by the configured Task/Source tables and affected pins, rather than by retained message payload size. Lost-state Queue/ring validation is cached once per Queue. Each ring reference resolves through exact-match binary search over the ordered record ranges, avoiding a full-history scan for every slot while preserving kind and readiness checks.

Task attachment and last-owner detachment now use this cleanup for valid core publication-bearing state. Replacement still acquires the native claim under the mutation gate before installing its incarnation. The OS lease remains the liveness authority. Task/Thread claims, historical acknowledgments, and Source counters follow the existing [ownership contract](native-storage.md#public-session-and-task-lifetimes).

## Qualification and remaining work

The [test guide](../test/README.md) distinguishes full-domain private delivery fixtures, deliberate corruption, and real process interruption from public API examples. Qualification covers exact tokens and counters, retained history after ring overwrite, full logs, old parent/Thread cleanup, partial absolute stores, replacement attachment, and repeated interrupted recovery. It tests process termination on a running local filesystem, without adding a power-loss durability guarantee.

Factories select **2.2/`0xf`** from step 4.8, allowing both recovery delivery and optional loss. Existing profiles are never upgraded in place. The [public receive contract](native-receive.md) explains view lifetimes, failure fencing, and gaps.

Step 4.9 adds [combined failure and exhaustion qualification](native-qualification.md), and step 4.10 demonstrates the public path in a [multi-process application](native-pipeline.md). The [milestone-4 completion review](milestones/milestone-4-completion.md) records the remaining API boundary; [performance measurements](native-performance.md) describe observed costs within explicit workloads. Neither qualification nor measurements add a lock-free, starvation-free, hard-real-time, or power-loss durability guarantee.

## Compact allowed-loss progress

[LoseRange validation and replay](https://github.com/smangano/angaria/blob/b4ec8ae/src/loss_redo.cpp) requires the separate allowed-loss capability, an idle consumer-owned Active Source, one Active allowed-loss Queue, and the exact overwritten nonterminal prefix. Its 48-byte command captures the inclusive range, loss timestamp, and Source identity. A following 32-byte WriteRange installs only the absolute terminal watermark and oldest-pending link. The complete transaction uses 80 encoded bytes regardless of the number of stale messages.

Validation scans retained Publication metadata and receipts before the first store, without reading payload bytes. The replay executor updates one receipt at a time instead of expanding the range into a command per message. Issued receipts reject loss; Acknowledged receipts remain unchanged. Lost receipts preserve historical dequeue identity and gain the same captured terminal time. Queue progress preserves the last actual acknowledgment time.

Committed replay accepts partially installed Lost state, presence, and time words, then reinstalls the full absolute values using the captured timestamp. It also accepts either old or new Queue progress words. Repeated interruption cannot produce a fresh timestamp, lose an in-flight pin, or resurrect a terminal obligation. Prepared rollback changes no receipt. Loss neither appends history nor reclaims space, and is available at a full log.
