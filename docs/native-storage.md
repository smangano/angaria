# Native storage resources and transactions

Steps 2.2 through 2.4 implement the private native resources and transactions used by the future format-2 backend. In the [file/mapping API](../src/native_file.h), `NativeFile` owns a native file descriptor, and `MappedRegion` owns a shared memory mapping. Both use move-only [RAII](glossary.md#encoding-and-native-resources): moving transfers ownership, and destruction releases the owned resource without throwing. The [controller](../src/session_controller.h) adds shared process-local ownership, the mutation gate, and Task lifetime claims; the [atomic adapter](../src/native_atomic.h) supplies native word access and ordering. The [mutation journal](../src/mutation_journal.h) uses those resources for recoverable operations.

A **file descriptor** is the process-local integer handle returned by the operating system when a file opens. A **mapped region** makes a file byte range accessible through virtual memory. Its returned **view** is a borrowed C++ byte span, not an owner. The [glossary](glossary.md#encoding-and-native-resources) defines the related terms, including inode identity, host pages, positional I/O, and mapping leases.

The file/mapping owners alone do not acquire the session mutation gate or interpret session contents. The controller validates immutable superblock metadata and native compatibility, but does not itself recover the journal or create a usable public Session. The separate journal implements transactions and recovery under a mutation guard. Direct resize and write primitives remain ordinary native I/O; callers do not gain committed Angaria publications by bypassing the journal.

## Files and access

| Operation | Behavior |
| --- | --- |
| `NativeFile::create_exclusive(path, max_bytes)` | Creates an empty regular file with exclusive creation. An existing path returns Conflict without truncation. Growth is a separate `resize()` operation. |
| `NativeFile::open_existing(path, access, max_bytes)` | Opens an existing regular file in explicit ReadOnly or ReadWrite mode. It never creates or truncates the file. |
| `size()` | Checks the descriptor's current file identity and length. The file must remain regular and within its supported byte limit. |
| `identity()` | Returns the opened file's device/inode identity. An inode identifies the underlying file independently of its pathname. |
| `native_handle()` | Returns a borrowed descriptor. Keep its owner alive while using it; callers must not close, replace, duplicate over, or resize that descriptor outside this API. |
| `read_exact(offset, output)` | Reads the complete requested range with positional I/O, handling short reads and interrupted calls. An unexpected end of file (EOF) is an error. |
| `write_exact(offset, input)` | Writes the complete requested range with positional I/O. It does not grow the file implicitly. |

The positive per-handle byte limit must fit the format's signed 64-bit range and the host's file-offset type. File ranges are checked with overflow-safe arithmetic before native I/O. Empty read/write spans are allowed at the end of the file; ranges beyond the current file length fail. A read or write that fails after I/O begins can have transferred part of its range. Higher layers need the journal protocol when atomic logical updates are required.

Descriptors are close-on-exec, so a successful [exec](glossary.md#encoding-and-native-resources) does not inherit them. The final pathname component cannot be a symbolic link. Nonregular files, including directories and named pipes (FIFOs), are rejected; nonblocking open prevents waiting on a pipe peer during validation. Read/write permissions and byte limits remain specific to each handle, even when another handle opens the same underlying file with different access. [Native open semantics](https://man7.org/linux/man-pages/man2/open.2.html)

## Mapping ranges and lifetimes

`map_read_only(offset, length)` and `map_read_write(offset, length)` require a nonempty range contained in the current file. A writable mapping also requires a ReadWrite file handle. `MappedRegion::bytes()` returns a read-only view; `writable_bytes()` returns a writable view only for a writable mapping.

The API accepts arbitrary byte offsets. It queries the host **page size**, rounds the native mapping offset down to a page boundary, checks the enlarged backing length against host addressable limits, and exposes only the originally requested span. This avoids assuming that the host uses 4,096-byte pages. Mappings request shared read-only or read/write protection, do not request execution, and let the OS choose the virtual address. The OS mapping requirements are documented by [Linux mmap](https://man7.org/linux/man-pages/man2/mmap.2.html) and [Apple mmap](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/mmap.2.html).

A mapping retains the originating file state, including its descriptor and range protection, after the `NativeFile` wrapper is destroyed or moved away. Its spans remain valid until the mapping's owning state is destroyed or replaced, subject to the coordination rules below. Moving a region transfers that lifetime without changing the mapped address. Move assignment releases the destination's previous mapping; spans borrowed from that previous mapping expire. Empty or moved-from owners reject access.

## Controlled resize and aliases

A **mapping lease** records the end of a live mapping's exposed byte range. Every handle for the same device/inode shares one process-local mutex and lease collection. This includes independent opens, alternate pathnames, and hard links. A mapping retains that collection through its backing file state.

Range validation, creation of a mapping and its lease, and resizing all use the same per-inode mutex. `resize(new_size)` permits growth, exact-size no-ops, and shrinking that leaves every live exposed range intact. Shrinking below the greatest leased end returns OwnershipBusy before `ftruncate`. Closing or replacing a mapping releases its lease. Growing the file does not enlarge existing spans; map a new range to access added storage.

Journal rollback must release any mapping created for an uncommitted append whose exposed range extends beyond the length being restored. The journal's transient append mapping is released on return or unwind before rollback attempts a shrink. Existing prefix mappings wholly below that boundary can remain alive during the shrink. Another retained mapping beyond the restore boundary can prevent rollback; an unresolved operation then requires further recovery.

The native resize primitive sets the exact file length and discards a removed suffix. Newly extended file bytes read as zero. This is file-length management, not proof of physical disk reservation or power-loss durability. [Native truncate semantics](https://man7.org/linux/man-pages/man2/truncate.2.html)

The mutex protects resource bookkeeping and the wrapper's I/O/resize operations. It does **not** synchronize direct reads and writes through returned mapped spans. Callers must coordinate shared data access separately.

Lease protection is process-local. Another process or code bypassing this API can truncate a file after it was checked. A previous size check cannot make retained spans safe against that race; do not access a span after uncoordinated truncation can have invalidated its range. Access beyond the shortened file can fault. The later mutation-gate and retention protocols coordinate cooperating participants; they cannot protect against arbitrary external truncation.

## Process ownership and fork

Files and mappings belong to the process that created their owners. Operations check that process identity before acquiring any inherited mutex. Inherited handles return WrongOwner. The process-local inode registry initializes on first use, including before `main`; once initialized, its factory calls also return WrongOwner in a fork child until the child execs a new program. A child whose parent never initialized native storage has no inherited registry to reject. A successful exec starts fresh storage state and removes inherited mappings.

This private layer does not implement general fork safety. After a multithreaded fork, the child must exec or call `_exit` before using this layer or cleaning up inherited C++ owners. The same cleanup restriction applies when a quiescent fork inherits an active mutation guard: its copied locked mutex cannot become child-owned. Inherited mutex or allocator state may have belonged to a thread that no longer exists. Mapping cleanup avoids locking the copied per-inode mutex in a child, but that does not make arbitrary post-fork C++ cleanup safe. Step 2.5 integrates recovery and bootstrap into usable public Session attachment.

## Shared controller and mutation gate

`SessionController::open_existing(directory)` opens an existing `session.ang`, `mutation.lock`, and `claims` directory. It decodes immutable [superblock](mapped-format.md#superblock) metadata, checks that the file contains its complete fixed-section prefix within the recorded byte ceiling, and compares its required features, storage mapping, synchronization version, and ABI profile with the native adapter. It does not create missing coordination resources or repair session contents. Exclusive creation of the session directory and its initial resources belongs to step 2.5.

Controllers are shared within a process by session identity and underlying file identity. Directory aliases resolve to the same controller. A live session copy or a conflicting set of coordination resources is rejected instead of silently introducing an independent mutation gate for the same session. Coordination files must remain stable; they are never unlinked or replaced by these primitives.

A **mutation guard** owns one acquisition of the [mutation gate](glossary.md#ownership-and-recovery). `acquire_mutation()` takes the controller's local mutex before exclusive `flock` on `mutation.lock`; `try_acquire_mutation()` attempts both without waiting for gate ownership and returns OwnershipBusy on contention. Nested acquisition on the owning thread also returns OwnershipBusy. The local mutex excludes threads even though they share a file-lock descriptor. Native ordering fences surround the protected work. Normal guard destruction releases the file lock before the local mutex, including when an exception unwinds the operation.

The guard retains its controller and is move-only. It is **thread-affine**: acquisition, use, moves, and destruction must stay on the acquiring thread. Destroying a live guard on another thread, or an unrecoverable native unlock failure, calls `std::terminate` rather than continuing with invalid lock ownership. `file(guard)` supplies a borrowed file owner for journal operations; the guard must belong to that controller and remain alive for the entire use. The resource API does not make arbitrary callbacks, mapped-span access, or unlocked file use safe.

## Task lifetime claims

`create_task_claim_file(guard, task)` creates or validates a stable `claims/task-<id>.lock` under the mutation gate. It is a resource primitive; it does not register a Task or persist an incarnation. `try_claim_task(task, parent)` opens that existing file through a distinct open description and attempts an exclusive nonblocking lock. A process-local claim table also rejects duplicate ownership. A different Task has an independent lifetime claim.

The returned shared `TaskLease` retains its controller. Its last owner releases the claim, so later Task handles, endpoints, and actor-bound Registry views can share its lifetime. A supplied parent lease is retained as well and must belong to the same controller and a different Task. Validating registered Task kinds and parent relationships, installing incarnations, and cleaning up predecessor state follow in the Session/Registry steps.

Operations with an existing Task retain its claim before taking the local session mutex and session file lock. Public attachment instead holds the mutation gate across a nonblocking new-claim attempt and incarnation installation, as defined by the [lock-order contract](concurrency.md#ownership-and-lock-order). `probe_task_claim(task)` returns whether a claim is busy; its native lock attempt never waits, including during recovery under a mutation guard. A free probe is only an observation, not a reservation. Claim attempts and probes return OwnershipBusy if their local claim bookkeeping is contended. Claim files remain present after their owners close. Nonblocking ownership attempts do not promise bounded filesystem I/O, allocation, or execution latency.

Controller lock descriptors are close-on-exec. Registered `fork` handlers close the child's inherited lock descriptors **without** issuing `LOCK_UN`, which would also unlock the parent's shared open description. This both preserves a live parent's exclusion and prevents a surviving child from retaining a dead parent's locks. Inherited controller/lease operations and factories bound to initialized parent state return WrongOwner. These handlers do not remove the multithreaded-fork restriction above. [Native fork-handler scope](https://man7.org/linux/man-pages/man3/pthread_atfork.3.html)

The descriptor registry has process lifetime because registered fork handlers cannot be removed and global owners can release their resources during static destruction. This retains the bookkeeping mutex and callback state until process exit; individual descriptors still close when their owners are destroyed.

## Native atomic qualification

`qualify_native_profile()` checks compiler/OS/CPU prerequisites: a recognized Linux or macOS x86-64/ARM64 profile, little-endian representation, 64-bit addresses and file offsets, and always-lock-free eight-byte compiler atomics. The result supplies the native `LiveCompatibility` used by the controller. It does not test an arbitrary filesystem or certify another build's environment. Qualification tests must run on the actual target; the four profile identifiers remain separate platform targets.

An **atomic word** is an indivisibly accessed, naturally aligned eight-byte value. `AtomicWord::bind(bytes, offset)` validates the complete range and eight-byte address alignment before returning a borrowed accessor. The caller retains the mapping and uses atomic access exclusively for that word. `load_acquire()` and `store_release()` provide the ordering required by record readiness. `publish_control()` uses a sequentially consistent store followed by a full compiler/hardware fence, ordering both the preceding body and subsequent state or resource effects. `native_gate_fence()` provides the gate-boundary ordering. See the [native ordering contract](concurrency.md#live-profiles-and-atomic-words) and [GCC atomic builtins](https://gcc.gnu.org/onlinedocs/gcc/_005f_005fatomic-Builtins.html).

These are explicit native ABI operations over coherent mapped storage, not portable serialization of C++ objects. Unsupported prerequisites and incompatible recorded profiles fail before session mutation. Successful atomic access does not flush storage or provide power-loss durability.

## Journal transactions and recovery

`MutationJournal` implements the reserved [operation journal](glossary.md#ownership-and-recovery) for two-plane storage. Its [portable codecs](../src/journal_format.h) encode the 256-byte journal header, redo commands, [record envelopes](mapped-format.md#arena-records-and-definitions), and append manifests with explicit little-endian fields. Live journal control and record readiness words use the native atomic adapter; codecs operate on local copies, never serialize native C++ structures, and do not read live control words nonatomically.

| Operation | Behavior |
| --- | --- |
| `MutationJournal::open(controller, guard)` | Retains the controller and maps the superblock. It requires that controller's active guard; opening alone does not recover or expose a public Session. |
| `recover(guard)` | Resolves an interrupted intent under the same gate. Idle ignores the old body, Prepared rolls back an unaccepted append or discards a validated inline intent, and Committed/Applied replays accepted work. |
| `snapshot(guard)` | Recovers first, then validates committed record framing/chains and captures generation, allocation tail, accounted bytes, Registry revision, manifest root, and physical file length. |
| `execute(guard, plan)` | Recovers the predecessor, rejects stale/invalid plans before a new intent write, prepares/materializes/commits the operation, and installs its absolute redo and final roots. |

A [transaction plan](glossary.md#ownership-and-recovery) contains a captured base snapshot, actor identity, absolute redo values, and any proposed records. Comparing the entire snapshot, including the completed **operation generation**, prevents a fixed-state update from leaving another plan apparently current merely because its tail and Registry revision stayed unchanged. A stale plan returns Conflict. Semantic/capacity rejection during preflight writes no new journal or canonical state; recovery of a predecessor may already have repaired that earlier operation before preflight begins.

FixedState keeps its complete nonempty command stream in the journal's reserved 1,792-byte inline area. It does not grow the file or change Registry revision, so a supported fixed-state update can run when append space is exhausted. An oversized inline stream returns CapacityExceeded rather than spilling into the arena. Filesystem, mapping, and counter failures can still prevent an update.

Append materializes an [append batch](glossary.md#ownership-and-recovery) of new records followed by a kind-11 manifest. Each record allocation is rounded to 64 bytes. The manifest lists every other record in order, stores the redo stream and actor/revision metadata, and links to the previous committed manifest. All records, the manifest, and padding count toward the recorded byte ceiling; insufficient space returns LogFull before preparing the intent. No committed logical address is reused.

The engine validates the entire command stream against its [redo target allowlist](glossary.md#ownership-and-recovery) before commit and again before replay. Generic WriteRange can replace only declared mutable words in selected superblock roots, supported fixed-state/index rows, ring slots, and publication receipt suffixes. It cannot modify immutable payload/definition bytes, reserved fields, the journal, or the allocation/accounting, Registry-revision, manifest, and completed-generation roots owned by the engine's final assignments. Each command retains one checked mapping for its complete range while applying its eight-byte atomic stores and fault checkpoints. These assignments and redo stores use absolute values, so recovery can repeat them without incrementing a counter twice.

Prepared rollback checks the persisted base generation, allocation tail, accounting, and Registry revision, the previous manifest derived from retained history, and the expected physical file range. FixedState also validates its complete inline command stream before discarding it. An Append's new records can still be incomplete, so rollback restores the original length without interpreting that unaccepted tail. The native journal does not persist a snapshot of every prior mutable table word; its base checks cannot detect arbitrary changes to all such words. Crash safety relies on cooperating writers holding the gate and making no canonical updates before Committed.

Committed or Applied recovery accepts new records already Ready or Committed and roots already holding either their base or proposed values. It validates the complete batch/manifest/commands before redo, repeats the common final assignments, then publishes Applied and Idle with the required following-effect fences. It never truncates accepted work. Invalid framing, unsupported persisted redo, or unexpected checked roots returns IoError while retaining journal evidence. Repeated recovery can itself be interrupted and retried.

If an I/O failure occurs after preparation, `execute()` attempts repair while retaining the gate. A proven precommit rollback returns the original failure; proven completion of an accepted operation returns its transaction result. If repair cannot establish either final state, it returns OutcomeUnknown and preserves the pending journal. An accepted operation must not become a known rejection merely because its caller lost the result. Public publication-outcome lookup is a later domain operation and is not supplied by this private journal API.

The initial implementation scans retained committed records to validate framing, batch generations, predecessor chains, manifest lists, and Registry revisions. This supports the no-reclamation baseline; it does not claim indexed or constant-time recovery/preflight performance. Task/schema existence, live actor claims, and definition/reference contents require the later Session/Registry/domain validators. The journal's checks are byte framing and allowed mutation checks, not complete semantic validation or general corruption detection.

Step 2.5 adds Task-only ReleaseClaim execution for FixedState operations. It validates registered Task references and ending incarnations, expands the compact intent into checked local absolute writes, and detaches the ending claim and its matching Thread Tasks. Detach timestamps precede flag stores; parent-incarnation tags remain available for repeated recovery. Each transaction may explicitly release a Task target only once, and writes to that target's incarnation must retain the ending value or install its immediate successor. Repeated targets and incarnation jumps return InvalidArgument before preparation, or IoError for malformed persisted intent, before any replay writes. This keeps every partial application within the executor's replay window. The compact persisted intent stays the same size for any configured Task count. It cannot change the Task index used for discovery or introduce delivery state. Steps 2.8–2.9 permit draft or active topology with zero delivery progress and valid zeroed rings; Publication/Retry records and nonzero delivery state still cause rejection until their domain cleanup is implemented. Task-only ReleaseClaim cannot combine claim cleanup with ring-slot writes. Other compact commands (ResetBudgets and LoseRange), Symbol-value records, SymbolIndex/StringPool updates, and segmented storage remain unsupported. Unsupported new intent returns UnsupportedPolicy; unsupported persisted replay returns IoError while retaining evidence.

`JournalFaultInjector` is a private test seam at [fault checkpoints](glossary.md#ownership-and-recovery): journal-body words, control transitions, file growth, record words/readiness, redo, final assignments, and rollback. Tests pause independent exec workers at actual boundaries and use SIGKILL, then interrupt and repeat recovery. They also inject I/O errors to check rollback, accepted completion, and OutcomeUnknown. Production Session callers do not supply these injectors; they are not external application callbacks executed under the gate. The tests exercise coherent local files on a running host, not power-loss durability or every possible hardware schedule.

## Public Session and Task lifetimes

`Session::create(options, creator)` validates programmatic options and the creator Process Task before creating resources. It exclusively creates a sibling [staging directory](glossary.md#ownership-and-recovery), initializes `session.ang`, `mutation.lock`, and `claims`, and holds the creator's native lease before bootstrap. A Registry Append stores the Session definition and creator registration. A FixedState operation installs incarnation 1 and the Session readiness flag. The completed directory becomes visible at the requested path through an atomic native rename that refuses to replace any existing target, including an empty directory, ordinary file, or dangling symlink. All owning result objects are prepared before publication.

Ordinary failure removes only that invocation's unpublished directory, after its file/claim owners close. A killed creator can leave an unpublished `.angaria-create-*` directory. Angaria does not automatically remove unknown staging directories or reuse them. Atomic publication and the journal address process termination on a running local filesystem; there is no synchronous power-loss durability promise.

The returned `CreatedSession` contains the Session and its attached creator Task (ID 1, Registry revision 1). Its immutable metadata records the opaque Session ID, creator Task, UTC creation time, effective OS user, framework version generated from `VERSION`, and application version. Explicit Session and Task codecs encode little-endian bodies and owned UTF-8 slices; they do not serialize native structs. Attachment recovers journal state and validates the Session definition, Task indexes/definitions, matching envelope/body/index revisions, complete Task state, and zero state in empty slots before exposing a handle. Its private gate-bound operation view (`RuntimeAccess`) builds one sorted index of committed record starts and decoded envelopes, reusing that index for all definition lookups in the operation. Lookup still rejects aligned addresses inside another record; Task-parent validation uses an ID-to-kind index instead of repeatedly searching the Task table. This removes repeated prefix traversal during Task validation while retaining the journal's linear retained-history scan baseline. It preserves metadata and creates no missing coordination files. `options()._directory` reports the actual canonical path, while the stored original directory remains diagnostic.

Session attachment holds no Task claim. `attach_task(id)` takes the mutation gate, validates the definition and parent relationship, attempts the native lease nonblockingly, and keeps the gate through installation of the next incarnation by FixedState. A status reader therefore sees the predecessor before acquisition or the committed successor after installation, with no interval pairing stale diagnostics with a pending lease. If installation fails, the provisional lease closes before the gate unlocks. First attachment uses incarnation 1 and restart count 0; each replacement increments both, resets claim-local publication issuance and retirement floor, and preserves registration history. `next_publication_id()` checks the live claim and counter, persists the next sequence through FixedState, and returns the claim-scoped identity. Overflow rejects before a new intent. Both operations work with an exhausted append log.

A Process Task permits coordinated calls from application threads. A Thread Task requires its local live Process Task, records that parent's incarnation, enforces its attaching thread, and retains the complete parent owner. Dependent actor Registry views retain their Task; Session Registry views retain the Session only. Task inspection probes native ownership under the gate, so a stale PID or attached bit alone never reports a live claim. Replacing a dead Process Task detaches Thread Tasks tagged with that ending incarnation. Last-owner destruction attempts a fixed-state detach before releasing the native lease and never throws. If detachment fails, ownership still releases and the next attachment can repair the recorded diagnostics. Fork children reject inherited operations before acquiring local mutexes; the earlier exec/cleanup restrictions still apply.

`TaskAttachmentObserver` is a private qualification hook after native acquisition and before the new intent. Test workers use it to pause a replacement, prove that an independent status reader finds the gate busy, and then commit, fail, or terminate that replacement. Production attachment supplies no observer. These tests coordinate through pipes and gate results rather than timing assumptions about which process runs first.

Step 2.5 implements Task lookup, description, registration metadata, and runtime status; subsequent steps add the remaining Registry operations below. File-based TOML factories are implemented in step 2.10 below. The current native policy profile supports two-plane storage, strict selection, spin waiting, recovery from log, and all-destination acceptance; other recognized policies return UnsupportedPolicy before creation. The portable codecs can inspect their stable wire codes without providing live execution support. Endpoint identities are implemented in step 2.9; publication delivery/status remain later work.

## Public Task registration

`Task::registry().register_task(descriptor)` validates the actor's native process/thread ownership before entering the mutation gate, then validates its persisted claim and any retained parent under that same gate. Session-bound Registry mutation returns ReadOnlyRegistry; an unbound Registry returns InvalidState. A shared pure descriptor validator supplies the same UTF-8 and kind/parent-shape rules used by the portable Task codec, without serializing or copying caller strings before the byte-budget check.

Names share one case-sensitive Task namespace. Exact name/kind/parent/documentation matches return the existing ID before checking remaining capacity, append headroom, or operation-counter exhaustion. They preserve the original creator, time, and revision, including for the bootstrapped creator. A differing descriptor under an existing name returns Conflict. A new Thread descriptor must name a registered Process Task; that parent may be offline or belong to another native process. Unknown parent IDs return NotFound, while an absent/zero parent, a parent of the wrong kind, or a parent on a Process descriptor returns InvalidArgument.

For a new registration, the gate serializes selection of the lowest unused Task ID and lowest empty allocation slot independently. Committed IDs and definition addresses are never reused for another entity. Registration preflights Task capacity, generation/revision overflow, and the complete definition plus manifest/redo/padding charge before creating coordination resources. LogFull and known semantic/capacity rejection leave this operation's canonical bytes and resource namespace unchanged; recovery of a predecessor may already have repaired earlier work. Registry strings consume arena history independently of the application string pool.

The new Task's stable `claims/task-<id>.lock` is created or validated under the gate before journal preparation, so every committed registration is attachable without repairing a missing file. Process termination or an ordinary I/O failure before acceptance may leave a [provisional Task claim file](glossary.md#ownership-and-recovery). It is not a registration or a held claim. A later registration can reuse that unpublished ID and stable file; Angaria never unlinks or replaces it. Such files are bounded by the recorded Task capacity and remain outside the log byte budget. The journal separately rolls back only its planned uncommitted arena growth.

One Registry Append stores a Task definition and final manifest, installs the current index entry, and advances the Registry revision once at Committed. Registration leaves the Task state row all zero and acquires no Task lifetime lease. Returned registration metadata records the acting Task, UTC registration time, and definition revision. Older definitions, their registration metadata, and the manifest chain remain retained across subsequent registrations and actor restarts. This preserves earlier Registry revisions; there is no Task descriptor-update or public historical-query API in this increment.

An interrupted registration is settled through the same journal recovery before lookup or another mutation. If a caller loses its result, `find_task(name)` and exact re-registration resolve the recovered identity without creating a duplicate; conflicting input cannot silently replace an accepted definition. Unresolved accepted repair returns OutcomeUnknown. The private `TaskRegistrationObserver` pauses after claim-file setup, and an optional private `JournalFaultInjector` exercises actual preparation, materialization, commit, redo, and recovery cuts. Public callers supply neither seam. The [public examples](../test/test_task_registration.cpp) and [independent-process tests](../test/test_task_registration_recovery.cpp) explain normal usage, no-write rejection, attribution/history, concurrent registrars, and repeated interruption.

## Fields and message schemas

Step 2.7 implements actor-bound `register_field` and `register_message`, along with Session/Task Registry lookup, descriptor inspection, and registration metadata for both entity kinds. The same native process/thread checks and gate-bound persisted-claim validation used by Task registration authorize mutations. Session views remain read-only. These operations create no coordination files or native Field/schema lifetime claims.

Fields use caller-supplied full 32-bit IDs with the `0xEE` high byte, including `0xEE000000` and `0xEEFFFFFF`. ID and name each identify one immutable descriptor. Exact ID/name/base/declared-size/documentation retry allocates nothing and preserves attribution/time/revision; a conflicting ID or name returns Conflict. The native implementation accepts char/byte (1 byte), int16/uint16 (2), int32/uint32/float32 (4), and int64/uint64/float64 (8). A mismatched size or unknown base code is InvalidArgument. Recognized opaque, temporal, compound, Symbol, and String representations return UnsupportedPolicy until their encodings are implemented. Portable codecs can inspect their stable codes without enabling native use.

Schema identity is an exact nonzero message type (`u16`) and version (`u32`). One message type retains one name across all versions; the name cannot identify another type. Identity, type/name pairing, ordered Field list, and documentation conflicts return SchemaConflict. Every Field reference must resolve; unknown well-formed IDs return NotFound and malformed prefixes return InvalidArgument. Order and repeated IDs are retained, empty control schemas are allowed, and a 65,536-element list needs no special encoding or larger count type. Versions can be registered out of numeric order and remain independently discoverable through their exact identities.

Before constructing a potentially large definition, registration validates input, current references, exact retries, capacity, generation/revision bounds, and the entire definition/manifest/redo/padding budget. Exact retries remain possible at LogFull and capacity/counter exhaustion. New Field/schema index slots are selected independently of sparse IDs and versions. Each successful call commits one immutable record and one final manifest, installs its index entry, and advances the Registry revision once. The method returns the already selected identity without allocating after commit. Ordinary I/O outcomes, OutcomeUnknown, and retry-by-identity use the same acceptance and recovery rules as other Registry appends.

Each new schema links to the latest registered definition of its message type; when a valid atomic batch shares one revision, record order resolves the latest predecessor. Older Field definitions and every schema version remain retained. Session attachment and read paths validate complete index rows, exact record boundaries/kinds, body/index/envelope revision agreement, creator registration, immutable Field identity/name uniqueness, scalar width support, schema type/name bijection and predecessor chains, and reference registration chronology. Every retained Field/schema definition must have exactly one index reference; clearing an entire row is corruption even when the remaining predecessor chain is valid. A schema may reference a Field defined anywhere in the same committed batch. The operation-scoped record index is reused for these lookups, and schema registration reuses one validated Field list for existing and new schemas; payload bytes and later encoding semantics are outside this metadata step.

The [portable tests](../test/test_schema_metadata.cpp) use independent byte fixtures, unaligned input, full-width identities, large repeated arrays, and malformed/overflow/canonical-slice cases. The [public examples](../test/test_schema_registry.cpp) demonstrate versioned definitions, no-write retry/rejection, exact byte limits, actor lifetime, and retained history. The [process tests](../test/test_schema_recovery.cpp) use an [independent worker](../test/native_schema_worker.cpp) for concurrent registrars and interruption at actual append/recovery/I/O boundaries. Native support remains limited to the qualified local-filesystem/process-crash contract, with no power-loss promise.

## Draft Queues and Queue Sets

Step 2.8 implements `register_source_set`, `register_queue`, and `register_publishing_set`, plus typed name lookup, description, registration metadata, `state`, and `source_members`. Registration requires a live actor-bound Registry, but the actor may describe an offline registered owner. Thread ownership rules remain in force. Zero owner/producer/source identities are permitted for incomplete drafts; nonzero identities must resolve to the appropriate registered kind. A nonempty Publishing set requires a nonzero owner and destinations whose producer matches that owner. Duplicate destinations return InvalidArgument and producer mismatches return WrongOwner.

Queue names are unique in their namespace. Source and Publishing sets share one name and nonzero 16-bit ID namespace, while consuming separate per-kind table capacities. Typed lookups do not reinterpret the other Queue Set kind. IDs are independent of allocation slots and are not reused. Names and documentation follow the Task metadata UTF-8 rules. Omitted policies and ring capacity resolve from recorded Session defaults; description returns effective values. Native registration supports strict/spin/recover-from-log/all-destinations; other recognized policies return UnsupportedPolicy. A Queue's positive ring capacity must have representable two-plane geometry, but registration allocates no ring or coordination file.

Exact effective descriptors return the existing identity before growth checks, preserving metadata, bytes, and counters. A changed descriptor or a Queue Set name of the other kind returns Conflict. Source membership is derived from Queue registration and is excluded from Source descriptor comparison. Queue registration with a Source commits the new Queue definition, revised Source definition, both index rows, and every occupied Source membership row in one Append. The Source revision advances while its creator and creation time remain fixed. The complete batch, manifest, redo commands, and padding are included in preflight before descriptor copies. Failures preserve prior definitions and relationships; uncertain accepted outcomes resolve through lookup and exact retry.

Initial Source member order follows Queue registration; later assignments append new members. Membership rows pack the Queue ID and priority, use the current Source definition revision, and leave flags/credits/reserved bytes zero. Publishing destinations preserve caller order; their rows have priority zero and the Publishing topology revision. A Publishing set starts at topology revision 1 and records its current immutable snapshot reference in reserved runtime state. Queue and Source progress rows remain zero. Empty allocation and membership slots remain zero.

Attachment and topology reads validate all retained predecessor chains, stable creation attribution/names, current-index completeness, Task/reference registration chronology, shared Queue Set IDs/names, membership capacities and both directions of each Source relationship, Publishing producer ownership, and runtime mirrors. A cleared latest index cannot hide a retained identity. Definitions in one atomic batch may share a revision and reference each other independently of physical order. Historical transition checks compare the final definition of each entity at that committed revision: removing Source membership and changing a Queue assignment must agree immediately, even if a later revision restores a valid graph. The operation uses cached committed record boundaries and owning decoded metadata. Step 2.9 extends these checks to Active entities and their resources below.

The [public tests](../test/test_topology_registry.cpp) teach the registration/inspection sequence and rejection behavior. [Portable codecs](../test/test_topology_metadata.cpp) use independent byte fixtures. [Process tests](../test/test_topology_recovery.cpp) and their [worker](../test/native_topology_worker.cpp) exercise independent discovery, same/different-kind concurrent registrars, Queue/Source atomicity, actual SIGKILL boundaries, repeated recovery, and I/O uncertainty. These retain the local-filesystem/process-crash scope of the native backend.

## Topology changes and activation

Step 2.9 implements draft ownership adoption, `assign_source`, `set_destinations`, all three activation operations, and Task endpoint opening/identity methods. Every Registry change validates its live actor and the complete recovered topology under one gate. Any live actor may complete draft ownership and activate configured entities for an offline registered owner. Adoption requires a nonzero registered target. Changed ownership is forbidden after activation; exact unchanged adoption/assignment/activation is an idempotent no-op. Changing a Queue's producer must preserve ownership of every Publishing set referencing it.

`assign_source` changes only a draft Queue. A zero Source ID explicitly unassigns it; a nonzero ID must name a Source set. Moving a Queue appends its new definition and both changed Source definitions in one transaction, preserving creation attribution/time and member order. New membership appends at the end; removal compacts the list and clears stale rows. A priority change in the same Source revises its membership mirror too. Active Sources accept fully configured draft members, but cannot become empty. Active Queue producer, Source, priority, capacity, and policy remain fixed.

`set_destinations` preserves unique caller order and producer ownership. Draft sets can become empty; nonempty sets require an owner. Active replacement requires the acting Task to own the set, even for an unchanged retry, and requires a nonempty list of Active Queues owned by that producer. An actual ordered-list change increments the Publishing topology revision exactly once; adoption and activation preserve it. Exhaustion never wraps the counter. The current definition reference and membership rows commit with the new snapshot. The shared gate supplies the serialization boundary for future publication calls.

Activation proceeds Source, then Queue, then Publishing set. A Source needs an owner and a nonempty list of fully configured members; those Queues can still be draft. A Queue needs a producer and an Active Source. Its transaction appends an Active definition and a kind-8 ring with zeroed slots/padding, installs the ring reference/capacity in Queue state, and advances the Registry revision once. A Publishing set needs an owner and nonempty Active destinations belonging to that producer. Incomplete definitions return InvalidState, inactive dependencies return NotActive, and space/resource failures leave the entity draft. Active is a one-way state under this contract.

Before copying definitions or allocating a ring buffer, mutation preflight accounts for all revised definitions, ring bytes, manifest references, redo frames, and alignment. Exact retries remain possible at LogFull and exhausted counters. Creation metadata stays fixed while the current definition revision advances. Shared append helpers give registration and updates the same checked byte accounting. No operation creates a coordination file.

Attachment validates the final topology at every committed historical revision, with all definitions from an atomic batch installed before relationship checks. State, ownership, and Publishing counter transitions compare final per-entity definitions at consecutive committed revisions; every retained record still validates its predecessor and stable creation attribution/name/time. Active ownership and policies are frozen, Source inverse membership stays consistent, and Queue producer changes cannot temporarily invalidate unchanged Publishing references. Ring references are unique, cover every retained ring, match their first Queue activation revision and exact geometry, and contain zero slots and padding in this pre-delivery implementation. Mutable resource checks use bounded atomic reads. Queue state stores only ring reference/capacity; Source state stays zero; Publishing state stores its topology revision and current definition reference. Other delivery state is rejected until implemented.

`open_writer`, `open_source_set`, and `open_publishing_set` require the matching owner and Active entity, then return move-only identity handles that retain the Task claim. Writer/Publishing openings can coexist; only one Source opening per set/claim is allowed. A claim-local mutex protects that exclusion, and closing or move-assigning the Source handle releases its old opening without persisted writes. Endpoints retain Thread affinity and parent claims. Plain `id()` throws `std::logic_error` for a moved-from or wrongly owned handle. Inherited-process use fails before a local mutex or gate is acquired. Send, publish, retry, receive, acknowledgment, release, and delivery cleanup remain declarations for their later milestones.

Task attachment validates the full topology before installing a claim, including through an already-held Session after external corruption. Task-only ReleaseClaim replay independently checks zero progress, current Queue definitions, exact ring capacity, geometry, and slots; equal rounded allocations cannot conceal a changed capacity. Task replacement and endpoint opening need no append allocation and work at LogFull. Future receipt cleanup will extend this idle-resource subset when delivery becomes available.

The [activation examples](../test/test_topology_activation.cpp), [endpoint lifetimes](../test/test_endpoint_runtime.cpp), and [independent-process tests](../test/test_activation_recovery.cpp) explain normal use, no-write failures, exact ring budgets, retained history, ownership/exclusivity, Task replacement, concurrent activation, and real interruption/recovery/I/O boundaries. Their private fixtures and fault hooks are clearly separated from application APIs.

## TOML Session factories

Step 2.10 adds `Session::create_from_file` and `Session::attach_from_file` using pinned cpptoml. The [configuration contract](configuration.md) defines exact types, required and optional keys, supported policies, and named references. The loader resolves names independently of declaration order and uses the common descriptor and native policy validators. Unknown keys, malformed values, duplicate identities, unresolved references, wrong ownership, unsupported policies, and exhausted capacities fail with configuration key paths.

File-based creation takes the name of a declared Process Task as its creator. That declaration supplies Task ID 1 and its reserved entry, and initial registrations retain its attribution. The factory registers Process Tasks before Threads, Fields before schemas, and complete topology before activation. Nonempty Sources activate before their Queues, then nonempty Publishing sets activate. Empty sets remain Draft. Registration and activation preserve their ordinary checked journal, ring-allocation, and byte-limit guarantees.

The complete setup runs before exclusive publication of the requested Session directory. A concurrent creator or existing target cannot be replaced. Ordinary failure cleans only that invocation's unpublished staging directory; a process terminated during setup can leave an unpublished staging directory, as with programmatic creation. No partial configured Session is published at the requested path.

File-based attachment resolves `session.directory` from the TOML file's parent, validates and recovers the existing Session, and compares effective name/application version, byte limit, storage/segment settings, capacities, and defaults. A mismatch returns `ConfigurationMismatch`; the actual canonical location may differ from its recorded creation path. Supplied declarations and references are checked with already registered names available. They do not reapply initialization, revert supported topology changes, or claim Tasks. The underlying validation/recovery path retains its normal write behavior.

The [file configuration tests](../test/test_file_configuration.cpp) explain public creation and attachment, rejection behavior, and preservation of existing state. The [primer lesson](primer.md#7-move-setup-into-a-toml-file) demonstrates the same operations without private fixtures. Configuring Active endpoints still does not implement payload delivery or scheduling.

## Failures and validation scope

| Result | Meaning here |
| --- | --- |
| `InvalidArgument` | Invalid path, access mode, byte limit, range/alignment, Task ID, parent lease, or transaction plan. |
| `InvalidState` | Empty/moved-from owner or guard, or a write, writable mapping, or resize attempted through read-only access. |
| `WrongOwner` | Inherited process ownership, a guard used on another thread, or a guard belonging to another controller. |
| `Conflict` | Existing exclusive-create path, conflicting live identity/namespace, or a stale transaction plan. |
| `CapacityExceeded` | Requested resize exceeds its byte limit, an operation counter is exhausted, or FixedState commands exceed the inline journal. |
| `OwnershipBusy` | Resize would invalidate a mapping, a gate/Task is already owned, or local claim bookkeeping is contended. |
| `UnsupportedPolicy` | A requested storage, record, or command operation has no live implementation yet. |
| `LogFull` | A complete proposed append, including its manifest and padding, exceeds the session byte ceiling. |
| `IoError` | Native I/O failure, invalid/replaced resources or metadata, unsupported native compatibility, unexpected EOF, or a range beyond the file. |
| `OutcomeUnknown` | An interrupted journal operation could not be proven rolled back or fully accepted/completed. |

Errors include a diagnostic path and message. Destruction releases descriptors and mappings without throwing. It does not delete the underlying file, perform journal rollback, or provide a synchronous durability flush.
